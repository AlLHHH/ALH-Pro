## 六、Findings

### F1 [high] 标定可能测到「生产根本不会走」的那条后端(探测失败时)

**事实(静态可证,行号精确):**

* 标定在前:`VideoService.cs:2204`(`if (doUpscale && frameInterp && upscaleRuns)`)内,`:2228` 用 **`gpuId`** 调
  `UpscaleBackendPlan.UseOnnx(engine, gpuId, calibPrefEsrgan, calibPrefWaifu2x, ncnnUnreliable: false, fastMode)`。
* ncnn/ONNX **探测在后**:`:2468 else if (doUpscale)` 内的 `:2499 int upGpu = gpuId;` → 探测
  (`EnsureNcnnProbeAsync`)→ 探测**失败**时改口:`:2591 upGpu = -1; :2592 upOnnxDml = true;`(非 waifu2x 分支)、
  `:2539 waifuOnnx = true; :2540 upOnnxDml = true;`(50 系 waifu2x 分支)、`:2605 waifuOnnx = true`(选 CPU + 50 系)。
* 批次循环在最后:`:2882` 用 **`upGpu`** + `waifuOnnx` 调同一个纯函数 ⇒ 探测失败时**走 ONNX(DirectML,`-2`)**。
* 于是:**当某台机器的首次"生产尺寸"探测失败时,标定仍按 `gpuId>=0` + `ncnnUnreliable=false` + `ShouldUseOnnx*()=false`
  判成走 ncnn ⇒ 标定测的是 ncnn,而这一趟任务真正跑的是 ONNX**。
* 为什么"首次"必然会踩到:`ShouldUseOnnxEsrgan()`/`ShouldUseOnnxWaifu2x()` 读的是**已落盘的探测结论**,且
  `treatBlackwellAsRiskyWithoutProbe:false`(`EngineService.cs:48-64`)⇒ 一台机器第一次跑时它**必然**是 false,
  而标定恰好只在"第一次/没标定过"时执行。
* 标定与生产**用的设备参数也不一致**:`:2246` 是 `gpuId < 0 ? -1 : -2`,而 `:2954` 是
  `upGpu < 0 ? (upOnnxDml ? -2 : -1) : -2`。在 `gpuId<0` 这条路上两者都是 `-1`(可达状态等价,不算缺陷);
  但在"探测失败"这条路上生产用 `-2`,而标定**压根没走 ONNX**(参上一条)⇒ 两者根本不在同一个后端上。

**影响(取决于那条坏路在采样尺寸下的表现,我无法在本机复现 ⇒ 见第八节):**

* 分支(a)**最重**:ncnn 在真实分辨率下"静默出黑帧、退出码 0"(本仓库已实测多次)⇒ 黑帧往往**更快** ⇒
  `TryBuild` 接受(0.0005 ≤ p ≤ 120)⇒ 把一条**错的、偏小的**单价当成"本机实测"**落盘**,而且是
  (模型×引擎倍率) 这一格的长期判据 ⇒ 判定偏向"补帧→超分"⇒ 正是 2026-09-25 真机事故(39 分钟 vs 10 分钟)那一类。
* 分支(b)较轻:引擎卡住/失败 ⇒ 最多白等 180 s、标定失败、当次回旧顺序;因为什么都没落盘,下一次还会再标一次——
  但从第二次起探测结论已落盘,`ShouldUseOnnx*()` 变真 ⇒ 那一次会正确地走 ONNX 标定。**只有分支(a)不会自愈**。
* 受影响配置恰好是本队章程最关心的那批:**50 系 / AMD / Intel / 无独显 / 探测失败而 DirectML 可用**的机器。

**requiredFix(建议,二选一):**
1. 把标定挪到探测之后:`upGpu / waifuOnnx / upOnnxDml` 定稿之后、`Decide(...)` 之前执行标定,并用
   `UseOnnx(engine, upGpu, onnxPreferredEsrgan, onnxPreferredWaifu2x, ncnnUnreliable, fastMode)` 判后端
   (即与批次循环**同一个输入**),ONNX 设备参数也照 `:2954` 的口径传。
2. 最小改动版:标定照旧在前,但在探测定稿后**复核后端是否一致**;不一致就丢弃这次标定
   (`Reject("后端与生产不一致,本次不采信")`),不要落盘也不要参与判定。
