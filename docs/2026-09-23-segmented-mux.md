# 分段合帧（空间不足时自动降级）设计方案

- 日期：2026-09-23
- 状态：**设计已获作者确认**（① 自动降级 + 一条明确提示 ② 保持并发 ③ 段上限 2000、按预算自动缩），**待实现**
- 相关：`ImgUpscalerUI/VideoService.cs`（视频管线）、`AlhPro.Core/TempSpaceEstimate.cs`（临时盘估算，2026-09-23 刚加过 `NeedGigabytesFor`）、`AlhPro.Core/RenderPolicy.cs`（`LimitBatchByTempDisk` 与 0.65 常数）
- 由来：用户反馈「不能补帧」（诊断包 `ALHPro_Diag_20260923_1345`，AMD RX 6750 GRE）：4K 源 + 2x 超分（输出 8K）+ 2x 补帧、约 5 分钟素材，预估 **262GB**，临时盘只剩 132GB ⇒ 守门在开跑前拒绝，6 次尝试全部 0.2 秒失败。

---

## 一、目标与范围

**目标**：把"临时盘放不下 ⇒ 任务直接失败"改成"**放不下就自动分段跑完**"。常规任务（放得下）**一行行为都不变**。

### 做

- 守门判定"预估 > 剩余"时，**不再抛异常**，而是在**同一套编码参数**下改成**按段编码 + 无缝拼接**；
- 段大小按剩余空间自动算（上限 2000 帧/段，沿用 2026-09-13 批准的口径）；
- 界面/日志给**一条明确提示**（自动进行，不要求点确认）；
- 分段模式的**真实峰值**要在日志里如实报出，便于事后核对。

### 不做（写清避免承诺落空）

- **不做**常驻编码器的"真·单遍封装"（那是另一条路线：峰值能压到几 GB，但要严格按槽位顺序喂帧，与现有并发/去重组的非连续性冲突）——留作后续独立一轮；
- 不改音频处理路径、不改编码器选择策略、不改黑帧回退链本身；
- 不因分段而改变**画质**（同一套编码参数、同一 `frInput`、逐帧内容应与单遍路径一致）。

## 二、背景与关键事实（都已在代码里核对过，带行号）

| # | 事实 | 证据 |
|---|---|---|
| 1 | 最终帧是**逐步落盘**的（这是本方案能压峰值的前提） | 旧顺序：超分逐批写 `workDir\upscaled`，收尾 `framesFinal = upOutput`（`VideoService.cs:3093`，**变量重指向、不拷贝**）；新顺序：补帧逐段写 `framesInterp`，`:3190 framesFinal = framesInterp` |
| 2 | 最终帧**按槽号密集编号** | `:2744` 用输入帧名改名 ⇒ `frame_000001.jpg`…；重复槽回填也按槽名写（`:2948+`） |
| 3 | 标称帧率**只来自 JPEG 输入的 `-framerate {frInput}`**，没有独立 `-r` | `:3742 var muxInput = $"-framerate {frInput} -i \"{framePattern}\""` |
| 4 | 音频/元数据/时长保护都在**最后那一次封装**里 | `-map_metadata 1 -map_chapters 1`、`-t muxDur`、faststart（`:3743` 附近） |
| 5 | **批 ≠ 连续帧区间**（去重开着时一个批的输出槽位散布在时间轴上） | `:2515-2529` 按 `repSlots` 切批、每项带 `slots` = 同代表帧的全部槽位；代码注释明确写过"同组成员不连续" |
| 6 | 「帧数对齐/防吞尾」是**读目录**判定的 | `:3443 Directory.EnumerateFiles(framesFinal,"*.jpg")` 与全局 `expected` 比对，然后补足末帧/删多余 |
| 7 | VFR 的 `setpts` 是**全局**表达式 | `:3571 vfrSetpts = BuildVfrSetptsExpr(finalDurs)`；Core 侧 `VideoPipeline.BuildVfrSetptsExpr`（`:250+`）有 **400 段上限**（避免 setpts 超 32767 字符命令行），超限回退 CFR |
| 8 | 视频时长靠**复制末帧补足**对齐源容器时长 | `:3463-3469` 时长基准 = 源容器时长；`:3449-3452` 末帧补足 |

> 事实 1 是本方案的可行性根据：如果最终帧是"最后统一搬运"到合帧目录的，那"早编码早删帧"就压不住峰值 —— 现在确认是逐步落盘，所以能压住。

## 三、触发与段规划（纯逻辑，`AlhPro.Core`，可单测）

```
并发数 c        = SafeRender.GetVideoConcurrency()
单帧占用 mb     = outFrameMB + srcFrameMB            // 与 TempSpaceEstimate.NeedBytes 同源口径
预算 mb         = 剩余GB × 1024 × RenderPolicy.BatchTempDiskShareLimit(0.65)
段帧数          = min( 2000, floor( 预算mb / (单帧占用mb × (c+1)) ) )
若 段帧数 < MinFramesPerSegment(50) ⇒ 仍然拒绝
        （用 2026-09-23 做的量化提示：给出"关超分/关补帧"各要多少 + 其它盘剩余）
```

- `c+1`：盘上最多同时有 `c` 个"已写入待编码"的段 + 1 个正在编码的段（见 §四的背压）。
- `MinFramesPerSegment = 50`：段太小则"每段一次编码器启动"(秒级/次)摊到每帧上不划算；50 帧 ≈ 1.7 秒素材，
  是"分段还有意义"的下界。低于它说明余量已经紧到任何分段都救不了 ⇒ 老实拒绝并给降级建议。
- 段是**连续的最终帧号区间**（`[a, b)`），**不要求与批边界对齐**（事实 5）。
- 段规划的结果写成不可变 record（段数、每段帧区间），供流水线与测试共用。

## 四、流水线改动（只在分段模式走新路）

1. **段的完成判据 = 该区间每一帧都已落盘**（位图/计数器），与批边界无关。
2. **背压（峰值可控的关键）**：在飞段数上限 = `c+1`；到顶时不启动属于下一段的批（等待）。没有这条，"编码追不上处理"时峰值会失控。
3. 段就绪 ⇒ 用**同一套编码参数**编码成 `workDir\seg\seg_000k.mp4`：
   - 同一 `EncoderArgs`、同一 `frInput`、同一条 `-vf` 链；
   - 用 `-start_number <段首> -frames:v <段长>` 直接读同一目录的连续区间 ⇒ **不为每段拷贝/硬链接帧**；
   - VFR 时 `setpts` 按段切片 + 加**段首累计时间偏移**（事实 7）；
   - 复用现有**编码器回退链**（`GetHwRecipe` / `BrokenHwEncoders` / 硬编失败退 CPU），否则某段失败=整任务失败；
   - 输出**视频轨、无音频**。
4. **编码成功后才删该段帧**；失败/取消不删。
5. **最后一段特殊**：在「帧数对齐/末帧补足」之后才编码（事实 6、8）；同时把该步的判定从"读目录"改成**按台账计数**，否则早期段已删会被误判成"输出不足"而疯狂补帧。
6. 全部段完成 ⇒ `ffmpeg -f concat -safe 0 -i list.txt -c copy` 拼出视频轨 ⇒ 套用**现有**的音频/元数据/时长/封装那一段。
7. 校验：`Σ 段帧数 == expected`（按台账），拼接后再用现有「输出校验」验帧率/时长/黑场。
8. 进度：新增一步「分段编码 k/N」，并如实报出分段模式的峰值估算。

## 五、已知副作用（必须只在分段模式生效并写清）

- VFR 的 `setpts` 400 段上限是**每条命令**的约束（事实 7）⇒ 分段后变成"每段 ≤400" ⇒ **分段模式下超长 VFR 表反而可用**（单遍模式仍回退 CFR）。这是行为差异，只在分段模式出现。
- 分段模式多 `N-1` 次编码器进程启动（每次秒级）⇒ 比单遍略慢；**长片 + 空间紧**时才用。
- 取消/失败时已编码的段文件留在 `workDir\seg\`，随 `workDir` 一起被清理（现有 finally）。

## 六、验收口径（必须逐条过，不许"应该没问题"）

1. **纯逻辑单测**：段规划（上限 2000、预算不越界、`c+1` 计入、连 1 帧都放不下⇒拒绝、区间首尾相接无空洞无重叠）。
2. **真机 A/B（分段 vs 不分段，同素材同参数）**：新增测试缝 `ALH_TEST_SEGMENT_FRAMES=<n>`（强制分段、指定段帧数）——
   - 帧数、时长、`r_frame_rate`、音画对齐（现有校验行）必须一致；
   - **逐帧比对**：段拼接件的每一帧与单遍成片对应帧应一致（解码后逐像素比对；若编码器同一套参数，理想情况逐帧字节相同）；
   - 日志里必须有"已自动改为分段处理"与每段完成行。
3. **VFR 专项**：各段 duration 之和 == 单遍成片 duration（误差 ≤1 帧）。
4. **标称帧率专项**：段与拼接后 `r_frame_rate` 一致（历史坑：127 帧塞进 2.7 秒 → 47.037fps → 全程顿挫）。
5. **默认路径回归**：跑一条**放得下**的常规任务（2K→4K 这类），输出与改前**逐帧一致**，且日志里不出现任何分段相关字样。
6. **黑帧/整批重跑**：分段模式下批计数可回退，"整批空产 ⇒ 整批重跑"仍生效。
