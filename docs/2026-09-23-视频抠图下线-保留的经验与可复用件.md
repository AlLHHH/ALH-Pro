## 一、为什么删(以及为什么不该再建)

1. **成本/收益不匹配**。整条链是"逐帧 ONNX 推理 + 全分辨率蒙版后处理 + 时序稳定 + 合帧编码"。
   本机(RTX 4060 Laptop)1080p 实测:`isnet-general-use` + GPU = **256 ms/帧(只出蒙版)**,
   加后处理/滤波/合成 **+96 ms** ≈ **0.35 秒/帧** ⇒ **60 秒的片子约 10.5 分钟**,CPU 要 **31 分钟**。
   而它要解决的问题(换背景/出透明通道)在剪辑软件里是常规操作,用户实测后判定不值得。
2. **页面从建立起就是锁着的**:2026-09-22 建好后一直挂"开发中 · 敬请期待"横幅 + 整页禁用,
   从未对用户开放过 —— 留着只是一个永远进不去的入口 + 一份要跟着维护的死代码。
3. **用户明确"以后不会再做"** ⇒ 不留页面骨架、不留"待续"开关。

## 二、保留的可复用件(这是本文件存在的理由)

### 1. `AlhPro.Core/VideoMatting.cs`(纯逻辑,保留)
`PostProcessAlpha`(阈值 → 羽化 → 形态学)、`Composite`(fg×alpha + bg)、`LooksLikeSceneCut`、
`AlphaTemporalFilter`(时域稳定,含"切点先 Reset")。

- **它不依赖任何 UI / ffmpeg / 显卡**,能在无 GPU 环境里被单测钉住 —— 单测就是它现在的**唯一消费者**
  (`VideoMattingAlphaTests` / `VideoMattingCompositeTests` / `AlphaTemporalFilterTests`,全部保留)。
- **将来哪里会用到**:图片抠图的边缘质量(同一套"阈值/羽化/形态学"数学)、任何"逐帧蒙版稳定"需求
  (时域滤波是治抖动的标准做法,实测**只花 3.9 ms/帧** ⇒ 几乎零成本)。
- 形态学部分做过 O(n·r²) → **O(n·r)** 的优化(可分离),这段实现在别处也用得上。

### 2. 抠图路径的"不允许瞎试设备"两道闸(仍在图片抠图生产中,没删)
`AlhPro.Core/DmlAttemptLedger.cs`(按 (模型, 设备) 记连击,连吃 3 次才不再试 DML,成功清零)
+ `CutoutService` 的**设备级熔断**(出现 `GpuFault.IsPersistentDeviceError` 那种持续性错误**一次即置位**)。
这套东西是本次实测**顺带修出来的真缺陷**(见 §三.3),对**图片抠图**一直在生效。

### 3. `_qa/mattingbench`(开发基准工具,保留在本机 `_qa`,不进装机包)
反射加载 `发布版\ALHPro.dll` 直接测**产品真实代码路径**的 ms/帧 —— 不复制算法,所以测的就是用户跑的那份。

用法与注意事项见本文件 §五。

## 三、实测数据(2026-09-22,RTX 4060 Laptop,1080p 探针帧,反射调产品代码)

### 3.1 四个抠图模型:速度与边缘质量

| 模型 | 输入尺寸 | GPU(DML) 稳态 | CPU 稳态 | GPU 加速比 | 软边像素占比 |
|---|---|---|---|---|---|
| birefnet-lite | 1024 | ✗ DML 失败 → CPU 回退 7.7~12.0 s | 4.9~5.4 s | — | 1.42% |
| **isnet-general-use** | 1024 | **0.40 s**(整条 `CutoutAsync` 路径) | 1.05 s | 2.6× | **8.13%** |
| u2net | 320 | **0.21 s** | 0.50 s | 2.4× | 1.37% |
| u2netp | 320 | **0.19 s** | 0.30 s | 1.6× | 2.86% |

⇒ 图片抠图页默认模型据此从 `birefnet-lite` 换成 **`isnet-general-use`**(按 key 指定,不动数组顺序 ——
界面设置里存的是**下标**,重排会让老用户的选择静默漂移)。这条改动仍在产品里。

### 3.2 "只出蒙版"与"完整路径"差多少(决定逐帧方案可行性的关键数)

| 模型 | 档 | 只出蒙版(推理+上采样) | 完整路径(含图片页后处理+写 PNG) | 差值 |
|---|---|---|---|---|
| isnet-general-use | GPU | **256 ms** | 374 ms | 118 ms |
| isnet-general-use | CPU | 930 ms | 1053 ms | 123 ms |
| u2netp | GPU | **66 ms** | 200 ms | 134 ms |
| u2netp | CPU | 184 ms | 310 ms | 127 ms |

⇒ **图片页那套后处理 + 写盘 = 120~134 ms/帧,跨模型基本恒定** ⇒ 任何逐帧场景都**必须绕开**
`CutoutAsync`/`PreviewMaskAsync`(它们会重复后处理,还会**每帧写一个 PNG**:1800 帧就是数 GB 临时盘)。

### 3.3 纯逻辑三段算法的每帧耗时(1080p,3 次取最快)

| 算法 | 参数 | 最快 ms/帧 |
|---|---|---|
| `PostProcessAlpha` | 只做阈值(fg=200/bg=64) | **11.1** |
| `PostProcessAlpha` | isnet 默认档(feather=1/morph=28) | **82.4** |
| `PostProcessAlpha` | 极值(feather=20/morph=100) | 183.5 |
| `AlphaTemporalFilter.Push` | stability 0/50/100 | 1.0 / 3.7 / **3.9** |
| `Composite` | fg×alpha + bg | **10.3** |
| 三段串联 | 默认档 | **95.7** |

⇒ ① 时域稳定几乎不花钱(≈ GPU 单帧推理的 1%),不必为"要不要开"做取舍;
② **羽化+形态学占后处理的 85%**(82.4−11.1)⇒ 将来嫌慢优先优化这一段(整数化/向量化/降分辨率蒙版),
阈值那段没必要动。

### 3.4 顺带修掉的真缺陷(对图片抠图一直有效)
`birefnet-lite` + DML 会失败并**静默回退 CPU**,更糟的是**它不一定报错**:连跑 5 次里 2 次抛异常、
其余几次"成功"但耗时 7.4~11.5 s(比纯 CPU 的 4.9~5.4 s 还慢 1.5~2 倍),用户完全看不出来。
且**失败会污染同进程后续所有 GPU 推理**:同进程先跑 birefnet-lite,紧随其后的 isnet GPU 从 **406 ms 掉到 1048 ms**(=CPU 速度);
释放那个失败的会话**救不回来** ⇒ 属**设备级**损坏(日志里 `887A0005 GPU 设备实例已经被暂停`)。
⇒ 修法见 §二.2;熔断后同进程内其它模型也不再试 DML,这是**有意**的(设备挂了那条路只剩 CPU 速度)。

## 四、逐帧处理永远适用的四条硬结论(与视频抠图无关,将来做任何逐帧 ONNX 都看这四条)

1. **同一 ONNX 会话不能并发 `Run`**(`CutoutService` 内部用 `SemaphoreSlim` 串行化)⇒ 逐帧推理与
   时序滤波必须在**同一个串行循环**里,别另起并行管线。
2. **推理耗时与分辨率无关(输入被缩放到固定尺寸),后处理与分辨率成正比** ⇒ 两条加速杠杆:
   **降分辨率预览**、**跳帧**(推理+后处理都按帧数线性下降)。拟合式(u2netp):推理 ≈28 ms + 后处理 ≈78 ms/百万像素。
3. **`_rawMaskCache` 对逐帧无效**:它按「图|模型|设备」缓存原始蒙版、超 8 张清空;逐帧每帧都是新键
   ⇒ 每帧写一张 1080p `float[,]`(≈8 MB)再立刻清空,纯属内存抖动。
4. **测 DML 必须"一个模型一个进程"**:一个进程里连跑多支模型,后面几支的 GPU 数字会被前面失败模型的
   设备级损坏污染成"CPU 速度",看起来像"GPU 没用"——第一遍全量扫描就是这么被带偏的。

## 五、透明通道编码的两个坑(如果将来又要出 alpha 视频,先读这段)

实测方法:造一张"左半不透明红、右半 A=0"的 RGBA 源图,按规格编码后再**解码抽 alpha 平面数点数**。

| 输出 | ffprobe 报的 pix_fmt | 抽出的 alpha | 判定 |
|---|---|---|---|
| WebM(libvpx-vp9 + yuva420p + `-auto-alt-ref 0`) | `yuv420p` ⚠ | 全透明 2400 / 不透明 2400 | ✓ alpha 在 |
| MOV(prores_ks + `-profile:v 4444`) | `yuva444p12le` | 全透明 2400 / 不透明 2400 | ✓ alpha 在 |

1. **WebM 的 alpha 不在 pix_fmt 里**:带 alpha 的 VP9 WebM 仍报 `yuv420p`,alpha 靠 `alpha_mode=1` +
   BlockAdditional 承载 ⇒ **别用 pix_fmt 判断透明通道有没有生效**(第一遍就这么误判了)。
2. **原生 `vp9` 解码器会静默丢 alpha**:同一份文件,`ffmpeg -i x.webm` 抽不出 alpha,
   `ffmpeg -c:v libvpx-vp9 -i x.webm` 才能抽出 ⇒ **将来任何"把成品再读一遍"的环节必须带 `-c:v libvpx-vp9`**,
   否则用户看到的是一份"黑底不透明"的片子,而且不报错。
3. 默认档当初定为 **MOV / ProRes 4444**(WebM 作备选):"认不认"取决于对方解码器 —— 连 ffmpeg 自己的
   原生解码器都静默丢 alpha。这条判断本身仍然成立,将来若要出透明视频还是这个取舍。
