## 一、目标与范围

给 ALH Pro 增加**第 5 个功能板块「视频抠图」**：把视频里的人物/角色从背景中分离出来，输出两种结果：

1. **换背景**：纯色 / 图片 / 另一个视频 → 输出普通 **mp4**（H.264 或 HEVC），微信/抖音/B站/OBS 都能直接播；
2. **透明通道**：输出带 alpha 的视频（**WebM / VP9-alpha** 默认；可选 **MOV / ProRes 4444** 最高画质）。
   > **2026-09-22 实测修正**：两条路的 alpha 都真实存在（编码往返数点数验证，见 `_qa/视频抠图_性能实测_20260922.md` §四），
   > 但注意 ①WebM 的 alpha **不在 `pix_fmt` 里**（ffprobe 仍报 `yuv420p`，靠 `alpha_mode=1` 承载）——
   > 别用 pix_fmt 判断透明是否生效；②**ffmpeg 原生 `vp9` 解码器会静默丢 alpha**，读回必须 `-c:v libvpx-vp9`。
   > 因"认不认"取决于对方解码器，给剪辑软件的默认档建议复议为 MOV/ProRes 4444（体积约十倍、到处都认），
   > WebM 留给网页/OBS/体积敏感场景。**2026-09-22 用户已决定：透明通道默认档 = MOV / ProRes 4444，WebM 为备选。**
   > 实现落在 `AlhPro.Core/MattingOutputSpecs.ForTransparent`（显式点名 `webm` 才走 vp9-alpha，其余一律默认档）。

### v1 做

- 多文件列表、逐条处理（与其它板块一致）
- 模型选择（复用现有 6 个 ONNX 抠图模型）
- 抠图参数：前景阈值 / 背景阈值 / 边缘羽化 / 边缘增强 / 形态学（**与图片抠图同一套口径与默认值**）
- **时序稳定**（治逐帧抖动的自研部分，见 §五）
- 时间范围选择、进度 + 预计用时 + 日志、暂停 / 取消、输出目录与命名
- 记住上次参数 + 重置（照其它页）

### v1 明确**不做**（写进文档与界面，避免承诺落空）

- 逐帧涂抹修正（透传到图片抠图页做单帧更合适，v2 再谈）
- 参数预设快照（v1 只做"记住上次 + 重置"；预设接入留 v1.1）

- 引入任何**视频专用**抠图模型（原因见 §三）

## 二、背景与关键事实（都是实测/查证过的，不是推测）

### 2.1 可复用的现成能力（本方案几乎零新增依赖）

| 现成件 | 位置 | 说明 |
|---|---|---|
| 抠图推理（纯 C#，ONNX Runtime，DirectML 可选） | `CutoutService` | 6 个模型注册表：BiRefNet-lite / BiRefNet / ISNet-通用 / ISNet-动漫 / U²-Net / U²-Net 轻量，含逐模型输入尺寸、归一化、输出名、logits 处理与参数预设 |
| 模型权重（1.68 GB，已随包分发） | `发布版/engines/rembg/models` | 许可均已登记在 `THIRD_PARTY_NOTICES.txt`（MIT / Apache-2.0 系） |
| 视频管线框架 | `VideoService` | 拆帧 / 逐帧阶段 / 进度心跳 / 临时盘清理 / 暂停 / 取消 / 时长保护 / 音频保留 |
| ffmpeg（含 alpha 输出能力） | `发布版/engines/ffmpeg` | 实测支持 `libvpx-vp9`、`prores_ks`、`qtrle`、`apng` 与 `yuva420p` / `yuva444p10le` 等带 alpha 像素格式 |
| 切点检测（场景切换） | `SceneCutJudge` / 转场阈值滑块 | 时序滤波在切点处必须重置，直接复用 |

### 2.2 被否决的路线：引入视频专用抠图模型

- **RVM（Robust Video Matting）是 GPL-3.0** —— 其 README 明写 "Code is re-released under GPL-3.0 license"。本软件是**自创专有许可**，引入 GPL 组件会传染整份软件 ⇒ **否决**。（先例：本项目曾因许可不明移除 Real-CUGAN。）
- MatAnyone / MatAnyone 2 等 2025-2026 的视频抠图 SOTA 多为**非商用/研究许可**，同样不能进专有分发 ⇒ 否决。
- 结论：**走通用单图模型 + 自研时序平滑**。将来若改变许可策略（开源或取得商业授权），再评估。

### 2.3 两个必须正面解决的约束

1. **中间帧是 JPG（无 alpha）**：`VideoService` 自 v1.2.1 起把中间帧统一存 JPG 以降临时盘 ⇒ 透明通道路径**必须把 alpha 单独成序列**（见 §四）。
2. **图片抠图的 GPU 路在本机是坏的，而 CPU 一张 4.9~5.4 秒（1024² 输入模型）**：`CutoutView.xaml.cs:168` 写的"强制 CPU"理由是"GPU 会占满显卡导致整机卡顿"。**2026-09-22 实测修正了这一条**（见 `_qa/视频抠图_性能实测_20260922.md`）：DirectML 其实可用，且对 `isnet-general-use` / `u2net` / `u2netp` 比 CPU 快 1.6~2.6 倍；但默认模型 `birefnet-lite`(1024²) 在本机 DML 上图融合失败(`8007000E`→`887A0005` 设备挂起)，一旦失败该进程内所有 DML 推理都退化成 CPU 速度。⇒ 视频抠图**可以走 GPU，但必须先确认 DML 真的健康**（§九 性能标定定为"用探针帧实测，而不是相信探测"），并把代价如实告诉用户。

### 2.4 实测结论（2026-09-22 标定，取代上文相关默认值）

| 项 | 实测值 | 依据 |
|---|---|---|
| 默认模型 | **`isnet-general-use`**（不是 `birefnet-lite`） | GPU 稳态 0.40 s/帧；`birefnet-lite` 的 DML 路已坏、CPU 要 4.9~5.4 s |
| ETA 系数 | **0.35 秒/帧**（isnet + GPU + 1080p：只出蒙版 256 ms + 三段算法 96 ms） | 1800 帧 ≈ 10.5 分钟；u2netp+GPU ≈ 0.16 s/帧（≈4.9 分钟）；isnet+CPU ≈ 1.03 s/帧（≈31 分钟）。**注意**：§一 那个 0.40 s/帧是整条 `CutoutAsync`（含图片页后处理 120 ms 与写 PNG）的数字，视频路径不用它 |
| GPU 默认 | **成立**（用户已选） | isnet 2.6×、u2net 2.4×、u2netp 1.6×；但设备级失败后必须熔断走 CPU |
| 加速杠杆 | 降分辨率预览 + 跳帧 | 推理耗时与分辨率无关（输入固定 1024/320），后处理与像素数成正比（≈78 ms/百万像素） |
| 透明通道默认容器 | **MOV / ProRes 4444**（备选 WebM/VP9-alpha） | 实测 WebM 的 alpha 连 ffmpeg 原生 vp9 解码器都会静默丢掉；ProRes 到处都认 |
| DirectML 失败处理 | **设备级失败一次即熔断 + 按 (模型,设备) 连击账本** | 实测失败后同进程 DML 全部退化成 CPU 速度且可能不报错；已修复并验证（提交 `ce3971f`） |

## 三、方案总览

```
                 ┌─────────────── 统一前半段 ───────────────┐
视频 → 拆帧(源分辨率) → 逐帧 ONNX 抠图(带状态) → 时序滤波 → 阈值/羽化/形态学
                                                              │
                        ┌─────────────────────────────────────┴─────────────────────┐
                        ▼                                                           ▼
        路径① 换背景：前景×alpha 合成背景帧                     路径② 透明：前景 RGB(JPG) + alpha(灰度 PNG) 双序列
        → 普通 JPG 中间帧 → 复用现有编码/封装/音频              → ffmpeg 合成 yuva → WebM(VP9-alpha) / MOV(ProRes4444)
        → mp4(H.264/HEVC)，音频保留/可静音                      → 音频：默认静音（可选保留）
```

- **不能与超分并行**：时序滤波需要状态 ⇒ 逐帧**串行**，进度按帧上报（与超分阶段的分批并行机制不同）。
- **路径①内部产出普通 RGB 帧** ⇒ v2 想接超分/补帧是天然的（v1 只在界面上不给开关）。

## 五、时序稳定（本功能的核心自研部分）

**问题**：现有模型都是单图模型，逐帧独立推理 ⇒ alpha 边缘在帧间**闪烁/呼吸**（尤其发丝、细边、运动模糊处）。

**做法（v1）**：对 alpha 做时域滤波，三个机制组合：

1. **帧差门控的 EMA**：`a_t = α·a_t + (1-α)·a_{t-1}`，其中 α 随该像素的帧间变化**自适应**（帧差大 = 真运动 ⇒ α 大、少平滑；帧差小 = 静止或抖动 ⇒ α 小、多平滑）。这样**静止区稳、真运动不拖影**；
2. **切点重置**：复用现有场景切换检测，切点处清空历史（否则后一个镜头会"继承"前一个镜头的 alpha ⇒ 可见鬼影）；
3. **边缘带保护**：只对"边缘带"（alpha 在 (0,1) 之间的区域）做时域滤波；实心前景/纯背景区直接取当前帧，避免整体拖影与半透明污渍。

**界面**：一条**稳定档**滑条（0~100，默认中档），ToolTip 如实写取舍："调大更稳（抖动更少），但快速运动边缘可能有轻微拖影；调小更跟手，抖动更明显。"

**边界**：首帧无历史 ⇒ 直接采用；场景内首帧同理；处理分辨率与源一致（不做隐式降采样）。

## 六、参数与默认值

- 抠图参数：**与图片抠图同口径**（前景 0~255 默认取模型预设、背景 0~255、羽化 0~20、边缘增强 0~100、形态学 0~100）⇒ 同一模型在两处给同样的默认值，避免"同一个词两个意思"。
- 模型默认：**BiRefNet-lite**（现有推荐档，动漫/真人通吃）。
- 设备默认：**GPU(DirectML)**，理由见 §2.3；界面同时提供「省电（CPU，很慢）」档，并**如实告知"处理期间显卡占用高，其它程序可能变卡"**。
- 输出：路径①默认 H.264 + 保留音频；路径②默认 **MOV / ProRes 4444**（到处都认，见 §2.4 实测），可选 WebM/VP9-alpha（体积小）与"保留音频"。静音默认：透明素材通常要有声时另配。

## 八、边界与失败处理

| 情况 | 处理 |
|---|---|
| DirectML 不可用 / 失败 | **设备级失败一次即熔断**（2026-09-22 实测：birefnet-lite 在 DML 上图融合失败后，同进程内 D3D 设备被挂起、所有 DML 推理退化成 CPU 速度且不一定报错 ⇒ 逐帧重试只是白等）＋明确告警 ＋ **ETA 重算**；已实现于 `CutoutService`（`AlhPro.Core.DmlAttemptLedger` + 设备级熔断），视频路径直接复用 |
| GPU 到底值不值得用 | **开工前用探针帧实测**，别信"探测通过"：实测 isnet GPU 0.40 s/帧 vs CPU 1.05 s（2.6×），而 birefnet-lite 的 GPU 反而比 CPU 慢 1.5~2 倍且不报错。判定"GPU 不划算"就直说并用 CPU，ETA 按实际档算 |
| 显存不足 | 按现有 `SafeRender` 思路降批/降分辨率，必要时退 CPU |
| 模型缺失 | 沿用图片抠图页的"模型缺失"提示条与安装指引 |
| 透明视频在多数播放器显示**黑底** | 界面明确写："要叠加请用剪辑软件（Premiere/剪映/DaVinci/OBS）" |
| 音频与时长 | 路径①复用现有音频保留与"时长保护"；路径②默认静音，若保留音频则用容器支持的编码 |
| 中途取消 | 复用现有临时帧清理机制，不留残留 |

## 附：本方案为何这样取舍（一句话版）

- **不引新模型** ⇒ 许可干净、体积不涨、当天可做；
- **两条输出路径分离** ⇒ 换背景走成熟 RGB 管线（稳、快、可叠加强化），透明通道单独处理 alpha（正确、可验证）；
- **时序稳定放 Core 纯逻辑** ⇒ 可单测、可调参、不与 UI 耦合；
- **先测量再定默认** ⇒ 不把"能用/不能用"赌在假设上。
