
















































































| 算出单价 ≤ 0.0005 或 > 120 s/帧 | 拒收(明显异常)⇒ 旧顺序 |
| 标定文件缺失 / 截断 / 字段非法 / schema 不认识 | `All()` 返回**空表**,绝不抛;逐条校验,坏的只丢坏的那条 |
| 落盘失败(权限/磁盘) | 只记日志:本次仍按刚测出的数字判定,下次要重标 |

**临时目录**:`<workDir>\calib_in` / `<workDir>\calib_out`,在 `finally` 里删 —— 成功、异常、取消三条路都删。

**标定耗时与记账**:标定单独记成阶段 `阶段耗时(准备·超分单价标定): X 秒`,并写明"含两次引擎启动、
**不是每帧速率**";标定过程**不接**引擎的逐帧 progress(免得被当成任务的帧率喂进 ETA 记账)。
留给调用方一个入口 `UpscaleCalibrator.LastTotalSeconds`(标定花掉的墙钟秒数)。

## 五、怎么看它生效了(用户视角)

一次"超分 + 补帧"的任务里,诊断日志(`%LOCALAPPDATA%\ALHPro\diagnostic.log`)会依次出现:

* 本机没标定过:
  `超分单价标定(准备阶段):引擎=realcugan 模型=models-se:0 倍率=2x、采样 9 帧(1920×1080 源)、机器指纹 …`
  → `超分单价标定:1 帧那次 2.55 s` → `超分单价标定:8 帧那次 14.10 s(平均 1.76 s/帧,含地板)`
  → `超分单价标定结束:耗时 17.3 秒(成功,结果已写入标定表);临时目录已清理`
  → `阶段耗时(准备·超分单价标定):17.3 秒(一次性;含两次引擎启动,不是每帧速率,不参与 PerfMemory 的每帧成本口径)`
  → `顺序判定:realcugan-se @ 2x(本机实测出处:本机实测 2026-09-25 21:03:11 两点法(1 帧 2.55s + 8 帧 14.1s,
     源 1920×1080)→ 1.65 s/帧@1920×1080,折算 1080p 1.65 s/帧) → u 1.65s > 门槛 0.2625s … → 选择 新顺序(超分→补帧)`
* 已经是标定过的机器:上面那段标定日志**不再出现**,判定直接引用文件里的记录(同一机器指纹)。
* 标定失败时:`⚠ 超分单价标定未取得结果:<原因> —— 本次保守用旧顺序(补帧→超分),任务继续`,界面日志区同时一句短话。

一眼确认"换机器会重标"的办法:把 `engine-prices.json` 里 `machineKey` 手改一个字 ——
下一次判定就会当成"另一台机器的标定,已忽略",并重新标一次(这个文件是给用户看的文本 JSON,不是二进制)。

**首次的代价(如实说明)**:第一次跑"超分 + 补帧"的任务(哪怕只是 3 秒预览)会**多花约 10~20 秒**做这次标定;
标定结果落盘后,同一台机器/同一引擎/同一模型倍率**再也不标第二次**(换素材、换分辨率、跑预览都是直接复用)。
界面在标定期间会显示一句短话「准备:正在按本机实测标定超分单价(<模型> <倍率>x,<N+1> 帧)…」,
所以它看起来是"在准备",不是卡死。

## 六、已知限制(逐条照 §5 写清,不许含糊)

1. **标定测的是"第 1 批"那条路**。批次循环每一批都会重新判 ncnn / ONNX,而且 `ncnnUnreliable` 可能在黑帧
   防御里**中途翻真**(之后各批改走 ONNX)⇒ 那时单价与实际会有偏差。这是既有行为,本轮**未修**(契约 §5.1)。
   标定用的是"开跑前的取值"(`ncnnUnreliable=false`,即第 1 批的真实取法),由纯函数
   `AlhPro.Core.UpscaleBackendPlan.UseOnnx` 决定走 ncnn 还是 ONNX —— 与批次循环**同一个判据、同一套参数**。
2. **`VideoPipeline.cs` 的 ETA 每帧常数仍是开发机数字**(只影响"预计剩余时间",**不影响阶段顺序**)。
   本机 `PerfMemory` 会在跑过一遍后用实测修正 —— 属另一条线,本轮不改(契约 §5.2)。
3. **采样帧来自本次素材**;换素材(分辨率/内容差异大)且面积折算不成立时会有误差。面积线性有本仓库实测支持
   (扣掉地板后比值 3.98 对 4.00,偏差 −0.5%~−7%),但**仍不是严格线性**(契约 §5.3)。
4. **两点法用两次进程启动,GPU 热降频会让两次的"地板"不同**(实测同机样本离散可达 1.9×)⇒ 标定结果按
   "一次快照"对待,**不**声称是永远准确的真理(契约 §5.4)。单价被拒收的边界(≤0.0005 / >120 s/帧)就是
   为这种脏样本设的兜底。
5. **【本轮新增 · 必须知道】`PerfMemory` 的样本里仍含这一次标定的墙钟时间。** `PerfMemory.Record` 在
   `Views/VideoView.xaml.cs` 里按"任务总时长 − 编码耗时"记账,而标定发生在这段窗口内(一次性,约 10~20 秒,
   且**只在第一次**——之后复用落盘结果)。本轮在**作用域内**做到的:标定单独记一个阶段、
   不与任何逐帧速率混算、并把耗时暴露成 `UpscaleCalibrator.LastTotalSeconds`。
   要让样本也把它扣掉,需要在 `Views/VideoView.xaml.cs` 的记账行加一句
   `processSeconds = Math.Max(0, taskSpan.TotalSeconds - encSeconds - <标定秒数>)` ——
   该文件**不在 t27 的 inScope 内**(契约只授权视频处理与 Core 侧),故**本轮不动**,在此如实标注。
   影响面:标定只在首次发生,且只让"每帧成本"这一条经验值偏大约 20s ÷ 任务总时长(短任务上相对明显);
   它只影响下一次的**预计时间**更保守,不影响阶段顺序判据。
6. **未验证的部分(如实标注,不含糊)**:
   * 真实机器上的长时间标定(本轮的标定逻辑只有单测 + 源码断言,没有在真机上跑过一次完整的两点法);
   * 50 系 / AMD / Intel + ONNX 路径下的标定数值(本机没有这些卡;`UpscaleBackendPlan` 的真值表有单测,但
     "ONNX 那条路上的秒/帧"没有本机实测);
   * 跑完第 1 批后因黑帧/显存切成 ONNX 时的单价漂移(见限制 1);
   * 用户取消标定瞬间引擎进程状态(逻辑上走 `finally` 清理并有超时兜底,但未在真机上复现过取消)。
