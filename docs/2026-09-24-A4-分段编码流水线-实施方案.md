## 0. 结论（先看这一段）

1. **现状的峰值不在编码阶段，在"最终帧全片落盘"那一刻**：守门的账（`TempSpaceEstimate.NeedBytes`：全片峰值帧 + 每批并存帧，×1.6）算的就是"最终帧全部同时在盘上"。编码阶段的分段（`VideoService.cs:5206 EncodeSegmentedMuxAsync`）跑得再早也没用——它是在**所有帧都处理完之后**才被调用（`:3930-3937`），此时峰值早已发生。
2. **只改守门（Task 3）解决不了这件事**：守门放宽只会让"本来会爆盘的任务"多跑一段再爆（`:503-508` 记录的 2026-09-15 事故：按 2x 放行、按 4x 跑，21048 帧里 8550 帧变占位帧）。守门要放宽，**前提是峰值本身降下来**。
3. **降峰值的唯一办法是让最终帧不必全片并存**：段一就绪就编码，编码成功立刻删该段的帧。段帧数由已经提交的纯逻辑 `MuxSegmentation.FramesPerSegment` 算（`:47-60`），它目前**只有单测在用**（`AlhPro.Tests/MuxSegmentationTests.cs`），生产路径只用了 `PlanSegments`（`VideoService.cs:5211`）——**接线点就是这里**。
4. **但"只把最终阶段改成流水线"是不够的一半**：最终阶段开始时，**上游阶段的输出是全量在盘的**（新顺序=超分输出，旧顺序=补帧输出）。所以方案分两期：
   - **一期（Phase 1）**：最终阶段按段生产 → 段就绪即编码 → 删段帧。峰值项从"全片最终帧"变成"上游全量 + (c+1) 段"。
   - **二期（Phase 2）**：让上游阶段与最终阶段重叠（上游当生产者、最终阶段当消费者），把上游在盘量从"全片"压到"1~2 段窗口"。**对 1x/2x（超分在前）这类配置，Phase 1 往往只剩临界余量，Phase 2 才是真正把任务救回来的那一步**（§四有账）。
5. **一句话**：峰值下降的本质是**把"最终帧全片并存"这一项按段截断**（Phase 1），**再把"上游全片并存"这一项按段截断**（Phase 2）；两项都由 `(并发+1) × 段帧数 × 单帧占用` 这一条已验证的口径约束（`MuxSegmentationTests.cs:28-30`）。

## 一、现状与失败路径

### 1.1 阶段顺序与"最终帧"是谁

| 配置 | 顺序（由 `AlhPro.Core.PipelineOrderPlan.Decide` 自动定，`VideoService.cs:2115-2121`） | 最终帧目录 | 生产粒度 |
|---|---|---|---|
| 1x / 2x（含 1x 修复） | **超分 → 补帧** | `framesInterp`（`:3224 framesFinal = framesInterp`） | 补帧按**转场分段**顺序跑（`segBounds`，`:2051-2057`），段内输出帧号全局递增（`:4918`） |
| 3x / 4x | **补帧 → 超分** | `upOutput`（`:3127 framesFinal = upOutput`） | 超分按**批**并行跑（`batchGroups`，`:2556-2563`；并发 `SafeRender.GetVideoConcurrency()`，`:2550`） |

两种顺序下，最终帧都是**逐步落盘**的（这是方案可行的前提，`docs/2026-09-23-segmented-mux.md:33` 事实 1 已核对）。

关键：**两种顺序里"最终阶段"启动时，上游阶段的输出都在盘上是全量的**——
- 新顺序：`InterpStageAsync` 被调用前，超分阶段已 `await Task.WhenAll(tasks)` 收尾（`:3115`），`upOutput` 里是全部 N 帧；
- 旧顺序：补帧阶段先跑完（`:2236` 调用点），`framesFinal` 里是全部 N 帧，超分再逐批读它（`:2412`）。

**结论（一期只能截断后半项，二期才能截断前半项）就在这一句里。**

### 1.2 峰值出现在哪一步（口径就是守门的账）

守门公式只有一份（`AlhPro.Core/TempSpaceEstimate.cs:54-60`）：

```
NeedBytes(peakFrames, peakFrameMb, batchFrames, sourceFrameMb)
  = ( peakFrames × peakFrameMb  +  batchFrames × (peakFrameMb + sourceFrameMb) ) × 1.6
```

`peakFrames` = 补帧后的全片帧数（`VideoService.cs:480`），`peakFrameMb` = `PeakFrameMegabytes`（`:479`）。也就是说守门按**"最终帧全片 + 每批输入/输出并存"**要空间——这正是最终阶段跑完那一刻的盘上状态：输入被逐批/逐段删掉（`:3062-3075`、`:1753-1766`），输出全量留存。

守门在两处判定、两处都会直接抛：

- 拆帧前粗判：`:606` → `EvalTempSpaceGate(true)`，抛在 `:587-588`；
- 倍率被「指定帧率」抬高后复判：`:1399-1403`（**这道才是拦住爆盘的那道**，`:1395-1398` 记录了理由）。

### 1.3 为什么"只改守门"不行（三条，都有现场）

1. **分段目前只作用于编码阶段**：`:3930-3937` 在编码分支里调 `EncodeSegmentedMuxAsync`；而它的进度分母 `encTotal` 是**数目录**得来的最终帧数（`:3899`）——说明调用时全部帧已在盘上。
2. **中途自动开分段 = 让注定失败的任务多跑一段再失败**：峰值发生在处理阶段，编码阶段的分段无法回收处理阶段已经占掉的盘。2026-09-15 的现场就是"低估 → 放行 → 跑到一半爆盘 → 后半段输出被占位帧顶替"（`:503-508`，21048 帧里 8550 帧占位帧）。
3. **现有实现自己也承认这一步没做完**：`docs/2026-09-23-segmented-mux-plan.md:192-197` 明确写「**仍未做**：① **边处理边编码**（把峰值从"全片最终帧"压到"段"的那一步；当前是"处理完再分段编码"，所以峰值还没降）」；`:239-258` 的 Task 3（接进守门自动触发）**全部未打勾**。`EncodeSegmentedMuxAsync` 的注释也写了同一句（`VideoService.cs:5204-5205`）。

## 二、目标形态

### 2.1 流水线形状

```
上游阶段（超分 或 补帧，整阶段或按段）
      ↓ 落盘
[最终阶段按段生产]  每一段吃自己那一段的输入
      ↓ 该段最后一帧落盘 + 该段的后处理（缩放/JPG 统一/AA）完成
[段就绪] → [段编码（同一套编码参数、无音频）] → 成功 → [删该段最终帧（+ 已被消费的上游帧）]
      ↓ 全部段完成
[concat -c copy] → [现有音频/元数据/时长/封装那一段]
```

- **段 = 连续的最终帧号区间** `[a, b)`，0 基，与 `-start_number`（1 基）直接对应（`MuxSegmentation.cs:36-40`）。
- **不按批切段**：去重开着时一个批的输出槽位可能散布在时间轴上（`VideoService.cs:2419-2431`、`MuxSegmentation.cs:12-16`），所以**段按帧号定义，批按段约束**（见 §三 S9）。
- **段就绪判据 = 该区间每一帧都完成了全部后处理链**（不只是"引擎写了文件"）：
  1. 引擎输出已落盘；
  2. 1x 修复的「缩回」（`：3136-3170`，只在超分阶段、且属上游/最终阶段内部）；
  3. 自定义输出分辨率缩放（`:3238-3259`）；
  4. 统一 JPG + 边缘抗锯齿（`:3262-3295`，`ReencodeDirPngToJpg`）。
  **第 2~4 步目前是"整目录一趟"**，必须先改成"按段一趟"，否则"段就绪"无从定义（这是本次改造里最容易被漏掉、也最容易做错的一步：漏掉它，成片就少了边缘抗锯齿）。

### 2.2 段大小从哪来

`MuxSegmentation.FramesPerSegment(freeDiskGB, peakFrameMb, sourceFrameMb, concurrency)`（`MuxSegmentation.cs:47-60`）：

```
预算 mb   = 剩余GB × 1024 × RenderPolicy.BatchTempDiskShareLimit(0.65)   // RenderPolicy.cs:161
单帧 mb   = peakFrameMb + sourceFrameMb                                  // 与 NeedBytes 同源
段帧数    = min(2000, floor(预算mb / (单帧mb × (并发数 + 1))))
段帧数 < 50 ⇒ 返回 0 ⇒ 保持"拒绝 + 给量化降级建议"（VideoService.cs:517-563 那段文案）
```

**接线点**（这就是"`FramesPerSegment` 现在只有单测在用"那句话的落点）：

| 现在 | 改成 |
|---|---|
| `MuxSegmentation.FramesPerSegment` 仅被 `AlhPro.Tests/MuxSegmentationTests.cs` 调用 | 守门里 `free < need` 时调用它：`> 0` ⇒ 规划分段；`== 0` ⇒ 保持原抛错（`:587-588`） |
| `PlanSegments` 仅被编码阶段的测试缝路径调用（`:5211`） | 在**最终阶段开始之前**调用一次，产出的段表作为全流程的段边界源（生产、编码、删帧、统计共用同一份） |

**段表必须在"倍率定稿之后、拆帧之前/最终阶段之前"一次性定格**：倍率被「指定帧率」抬高后 `peakFrames` 会变（`:1399`），段表若按旧倍率算就会偏大 ⇒ 段表要在 `:1399-1403` 那道复判之后生成。

### 2.3 两条必须同时满足的约束（峰值可控的关键）

1. **在飞段数 ≤ 并发数 + 1**（`c+1`）：盘上最多 `c` 段"已落盘待编码"+ 1 段"正在编码"（`MuxSegmentation.cs:44-46`）。到顶时**属于下一段的批/段必须等待**，不许继续生产——没有这条，"编码追不上处理"时峰值会失控。
2. **批不许跨段**：生产批的最小单位是"批"，段就绪只能等最后一批完成；批若跨段，背压窗口就失效。所以：
   - 超分作为生产者时，`batchSize` 必须钳到 `≤ 段帧数`，并按段切 `batchGroups`（`:2556-2563`）；
   - 补帧作为生产者时，段边界必须**加进** `segBounds`（现在只按转场切，`:2051-2057`），按"输出帧数 ≈ 段帧数"把源区间切块。

- **验收**：新增接线契约测试（照 `AlhPro.Tests/PreviewPairSyncTests.cs` 的"读源码 + 断言关键 token"写法）：① 不设缝时源码路径里不出现段编码调用；② 段编码调用点出现在最终阶段代码之前；③ 段命令里的 `encArgs`/`vfArg`/`frInput` 与单遍路径同源。

### S3 · 门控条件：什么情况下才允许走流水线（**保守即可，宁可拒绝**）

新增一个判定（在段表定格处一起算），全部条件都满足才走流水线：

1. `vfrSetpts == null`：即 `!preserveRhythm` 或时长表退化（`:3583-3638` 决定）——**沿用现有测试缝的门槛**（`:3890-3892`），理由是"按段切 setpts 要处理累计时间偏移，没有验收素材不做"（`:5201-5202`）。
2. `!tempoResample`（节奏重采样）：输出帧率由 tempo 路径在阶段内给出（`:3371`），阶段前不可知。
3. `!flatPlan.Flatten`（平滑时间轴）：`flattenActive` 在阶段内才置位（`:1612`），但**决策**在阶段前已定（`:2095`）⇒ 用决策判定。
4. `v4Interp && trueFrames > 0`：这样"帧数对齐"会把帧数**钉到 `expected`**（`:3466-3496`），最终帧数在阶段前就可确定。非 v4 路径的帧数由引擎产出决定（`:3352-3369`），不可提前 ⇒ 不进流水线。
5. `frameDurs == null` 或 `!(dedup && frameDurs.Count == frameCount)`（否则 `preserveRhythm` 会为真，第 1 条已排除）。
6. 计划帧数 `expected` 与 `muxDur`/`baseFps` 的自检通过（见 S6 的两条预校验）。
7. `FramesPerSegment(...) > 0` 且 §2.3 的两条约束可满足。

- **为什么**：任一条件不成立时，"最终帧数/帧率"都只能在阶段末才知道，而流水线要求段编码命令的 `-framerate` 与总帧数从第一段起就固定（各段必须同值，`docs/2026-09-23-segmented-mux-plan.md:23`）。
- **不满足时**：保持现状行为（放得下=单遍；放不下=拒绝 + `:517-563` 的量化建议），并**在日志里写明是哪一条门控没过**（否则用户看到"没自动分段"会以为功能坏了）。

### S4 · 最终阶段"按段生产"（两条路径）

**S4a · 补帧是最终阶段（新顺序 1x/2x）**

- **文件/方法**：`VideoService.cs:1516 InterpStageAsync`（循环体 `:1655-1794`）。

### S6 · 尾部步骤：按台账、且只施加在最后一段

以下四处的判定目前都靠**数目录**，段帧一旦被删就会被算错：

| 位置 | 现在 | 改成 |
|---|---|---|
| 帧数对齐（`:3466-3496`） | `Directory.EnumerateFiles(framesFinal)` 求 `seq.Length`，与 `expected` 比，补末帧/裁尾 | 用**台账**（`ReadyFrames`）比 `expected`；补/裁只作用在**最后一段**的帧号尾部 |
| 尾帧容积 / 裁尾（`:3510-3575`） | 同上（`seqA.Count`） | 用计划帧数预判 `add = round(muxDur × outFps) − expected`：`1 ≤ add ≤ 3` ⇒ 记成"最后一段的额外帧数"（`tailAddFrames`），编码最后一段时把它加进 `-frames:v`；`add ≤ 0` ⇒ 预告最后一段少产 `-add` 帧；`add ≥ 4` ⇒ **不满足门控，不进流水线**（这就是 S3 条件 6 的第一条预校验） |

### S7 · 进度/ETA 与统计口径

- **进度**：段编码时 `RunAsync` 报的 stage 名是 `分段编码 k/N`（`:5234`）。`ProgressBands.OfStageName` 用 `Contains("编码")` 映射到 `Stage.Encode`（`AlhPro.Core/ProgressBands.cs:75`），而该段区间是 `PostEnd..EncodeEnd`（`ProgressBands.cs:57`）——**处理还在 45~90% 时，一条段编码进度就会把进度条拽到 96%+**，随后处理进度又把它拉回来 ⇒ 进度条来回跳。改法（三选一，需评审）：

## 四、峰值盘占用的前后账

### 4.1 公式（全部用现有口径，不新造第二套）

- 单帧口径：`S = TempSpaceEstimate.SourceFrameMegabytes(srcW,srcH)`（`:27-32`）；`P = TempSpaceEstimate.PeakFrameMegabytes(srcW,srcH,outMult,frameInterp)`（`:35-41`）。
- **现状（守门口径）**：`NeedBytes = (N×P + batch×(P+S)) × 1.6`（`:54-60`），`N = peakFrames`（`:480`）。
- **上游在盘量**（Phase 1 必须计入，Phase 2 后按窗口计）：
  - 新顺序（超分在前）：`U_all = N_src × U`，`U = PeakFrameMegabytes(srcW,srcH,outMult,false)`，`N_src` = 源帧数；
  - 旧顺序（补帧在前）：`U_all = N × U_old`，`U_old ≈ SourceFrameMegabytes(...)`（补帧输出的引擎直出 JPG 口径，见 §八.5 的口径待定项）。
- **流水线（分段）峰值**：
  ```
  Phase 1:  峰值 ≈ U_all  +  (c+1) × 段帧数 × (P + S)
  Phase 2:  峰值 ≈ (1~2) 段 × U  +  (c+1) × 段帧数 × (P + S)
  ```
  这里的 `(c+1) × 段 × (P+S)` 就是 `MuxSegmentationTests.cs:28-30` 已经写进单测的那条分段峰值口径（它用的是 `(并发+1) × 段帧数 × 单帧占用`），**不另立一套**。
- **段帧数求解**（本方案对现有公式的**唯一要求**）：先按 `FramesPerSegment` 算出候选值（≤2000），再检查"峰值 ≤ 剩余空间"；不成立时**缩小段帧数**再解一次（而不是无脑放行或直接拒绝）：
  ```
  (c+1) × 段 × (P+S) ≤ free − 上游在盘量
  ```
- **段文件体积**：`K` 个段各是一份编码后的视频轨，体积 ≈ `码率 × 段时长`。以上面 4K 例（段 2000 帧 @60fps ≈ 33 秒、8K HEVC 约 30~50 Mbps）估 **≈0.2 GB/段、10 段 ≈2 GB**，相对百 GB 级可忽略；但要在 §八.7 确认是否入账。

### 4.2 例 1：真实用户案例（4K → 2x 超分(8K) → 2x 补帧，5 分钟）

数字来自 `AlhPro.Tests/MuxSegmentationTests.cs:11-12`（诊断包 `ALHPro_Diag_20260923_1345`）：源帧 9340、`N=18680`、`P=8.93MB`、`S=4.00MB`、批大小被面积缩放到 70 帧、`c=2`、临时盘只剩 132GB。

| 口径 | 计算 | 结果 | 判定（free = 132GB = 135168MB） |
|---|---|---|---|
| 现状（守门） | `(18680×8.93 + 70×12.93) × 1.6` = 268348 MB | **262.1 GB** | **拒绝**（与诊断包的"约 262GB"一致） |
| Phase 1（新顺序，上游=超分输出全量 9340×4.0=37360 MB） | `37360 + 3×2000×12.93` = 114940 MB | **112.2 GB** | **能跑**（10 段，留 19.9 GB） |
| Phase 1（旧顺序，上游=补帧输出全量 18680×4.0=74720 MB） | `74720 + 3×seg×12.93 ≤ 135168` ⇒ `seg ≤ 1559`，取 1559（12 段） | **132.0 GB** | **临界**（余量 ≈0） |
| Phase 2（上游窗口 1~2 段） | `3×2000×12.93 + 2×1000×4.0` = 85580 MB | **83.6 GB** | **能跑且宽松**（10 段，留 48 GB） |

**结论**：同一个任务，现状 262GB 被拒；只做 Phase 1 时"新顺序能跑、旧顺序临界"；**做 Phase 2 才回到从容**。
（`U=4.0MB` 的解释：`PeakFrameMegabytes(3840,2160,2.0,false)=max(4.0, 4.0×4×0.18=2.88)=4.0`，即被"不低于源帧"的下限兜住。）

### 4.3 例 2：1080p 长片（1080p → 2x 超分 → 2x 补帧，10 分钟）

构造：源 18000 帧（600s @30fps）、`outMult=2`、`frameInterp=true`、`N=36000`、批 700 帧、`c=2`、临时盘只剩 30GB（"小盘/临时盘被别的东西占着"的常见形态）。

| 口径 | 计算 | 结果 | 判定（free = 30GB = 30720MB） |
|---|---|---|---|
| 单帧口径 | `S=1.0`；`P=max(1.0, 1.0×4×0.18×3.1)=2.232MB` | — | — |
| 现状（守门） | `(36000×2.232 + 700×3.232) × 1.6` = 132183 MB | **129.1 GB** | **拒绝** |
| Phase 1（上游=超分输出全量 18000×1.0=18000MB） | 解得 `seg ≤ 1311`（28 段）：`18000 + 3×1311×3.232` = 30711 MB | **30.0 GB** | **临界**（段被压到 1311 帧，28 次编码器启动） |
| Phase 2（上游窗口 2 段） | `seg=2000`（18 段）：`3×2000×3.232 + 2×1000×1.0` = 21392 MB | **20.9 GB** | **能跑且宽松**（留 9.8 GB，段取到上限 2000） |

**结论（这是"Phase 1 不够、Phase 2 必须做"的最直观证据）**：本例 Phase 1 只剩临界余量、且段被压到 1311 帧（比上限小 35%）；Phase 2 才能把段拿回 2000、峰值再降 9GB。

### 4.4 结论性判断

- 峰值下降的**机制**：把"最终帧全片并存"（`N×P`）换成"(c+1) 段最终帧 + 段内输入/输出并存"（`(c+1)×段×(P+S)`）——`N×P` 那一项是百 GB 级，`(c+1)×段×(P+S)` 被 0.65 额度锁在预算内。
- **收益大小取决于两项的比值**：`P` 明显大于上游单帧口径 `U` 时（高倍率超分 + 补帧，`P/S ≈ 2.2`）收益最大；`P ≈ U`（如 1080p 2x 不补帧，模型给 `P = S = 1.0`）时，"最终帧全片"与"上游全片"是同一量级，**Phase 1 的收益只来自上游随段递减的那部分**。
- **必须如实计上游**：不计上游就是重演"低估 → 放行 → 中途爆盘"（`:503-508`）。

## 六、怎么安全验证（不制造真机爆盘风险）

### 6.1 测试缝（沿用本仓纪律："只认环境变量、进程内读一次、不设时零副作用"）

| 缝 | 作用 | 依据/纪律 |
|---|---|---|
| `ALH_TEST_SEGMENT_FRAMES=<n>`（**已有**） | 强制分段、指定段帧数，绕过守门；用于 A/B | `:3880-3897`；与 `ALH_TEST_VIDEO`/`ALH_TEST_SPLIT`/`ALH_TEST_KEEP_BAR` 同一套纪律 |
| `ALH_TEST_TEMP_FREE_GB=<x>`（**建议新增**） | 把守门看到的"可用空间"替换成 x，从而在**真机只有大余量时也能跑到"空间不足"的分支**，且不必真去填满盘 | 不加这条就只能真的塞满盘/找小盘；2026-09-15 的代价（`:503-508`）说明"真爆盘验证"不能再做一次 |
| `ALH_TEST_PEAK_SAMPLE_MS=<ms>`（**建议新增**） | 峰值采样间隔（见 6.3），默认关闭 | 现有 `USampleTemp()`（`:3229`、`:3716`）只在阶段边界采样（`:4064-4065` 自称"采样下界"），段级峰值采不到 |
| `ALH_TEST_SEGMENT_PIPELINE=1`（**建议新增**） | 强制启用流水线（不等守门拒绝），用于小素材 A/B | 与 `ALH_TEST_SEGMENT_FRAMES` 同款（后者已能强制分段，但走的是"处理完再分段"的老路径） |

**不加缝也能做的真实验证**（无风险）：把「临时盘」设置指到一块**真的小容量设备**（U 盘/小分区）——`PickTempRoot()`（`:5377`）走 `EngineService.TempRoot`，而"其它盘剩余"的提示本来就在教用户换盘（`:543-558`）。

### 6.2 小素材 A/B（逐条判据）

素材用 `ffmpeg -f lavfi -i testsrc2=size=1280x720:rate=30:duration=4`（照 `docs/2026-09-23-segmented-mux-plan.md:228`），配 2x 超分 + 2x 补帧，跑三遍：

| 组 | 命令 | 判据 |
|---|---|---|
| ① 单遍 | 不设缝 | 基准 |
| ② 处理完再分段 | `ALH_TEST_SEGMENT_FRAMES=60` | 与①逐帧一致（已有 52.46 dB 记录，`docs/2026-09-23-segmented-mux-plan.md:194`） |
| ③ 流水线 | `ALH_TEST_SEGMENT_FRAMES=60` + `ALH_TEST_SEGMENT_PIPELINE=1` | 与①逐帧一致（PSNR ≥ ② 的水平）；**输出帧数、时长、`r_frame_rate` 三项完全相同**；**音画对齐**走现有校验行（`:4126-4145`）；**帧号连续性**：抽帧后按帧号逐帧比（错开一帧应显著掉 PSNR，参照 27.54 dB 的既有记录） |
| ④ 流水线 + 后处理 | ③ 再开边缘抗锯齿（`postAa>0`）与自定义分辨率 | 与"① 同样开 AA/自定义分辨率"逐帧一致 —— **专测 S5（后处理按段）有没有漏** |
| ⑤ 上游降级 | ③ 中途触发 `ncnnUnreliable`（换一张不稳的卡/构造黑帧） | 段边界与帧号不变；后续批次改走 ONNX 的那一段输出与①一致 |

### 6.3 峰值盘实测（必须报真数）

- 采集：后台按 `ALH_TEST_PEAK_SAMPLE_MS` 采 `DriveInfo(tempRoot).AvailableFreeSpace`，取"初始剩余 − 最小值"（与现有 `uPeak` 口径一致，`:4083-4086`）。
- 判据：`实测峰值 ≤ 分段公式计算值 × 1.15`（允许 15% 裕度：样本间隔 + 段文件 + 批并存项的估算误差）。**不满足就是公式或背压有问题，不是"差不多"**。
- 对照：同一素材在"① 单遍"下的实测峰值应≈守门值（验口径本身没漂）；在"③ 流水线"下应≈ §四 的 Phase 1 公式值。

### 6.4 验收判据汇总（缺一不可）

1. **输出正确性**：帧数 = `expected`（台账口径）、时长 = 源容器时长（`:3500`）、`r_frame_rate` 各段与拼接后一致（历史坑：`docs/2026-09-23-segmented-mux.md:99`）。
2. **逐帧一致**：流水线产物 vs 单遍产物，逐帧 PSNR ≥ 既有 A/B 水平；错开一帧比对必须显著变差（证明无丢帧/重帧）。
3. **音画对齐**：现有校验行（画面时长 vs 源容器、音频流时长，`:4126-4145`）无告警。
4. **峰值**：§6.3 的实测判据。
5. **默认路径零变化**：跑一条放得下的常规任务，输出与改前逐帧一致，且日志里不出现任何"分段/流水线"字样。
6. **单测**：`dotnet test AlhPro.Tests/AlhPro.Tests.csproj`（含新增 `SegmentLedgerTests`、`MuxSegmentationTests`、以及 S2 的接线契约测试）。

## 八、需要人定/我没搞清的问题（诚实列出）

1. **分段模式守门要不要保留 1.6 安全系数？** 现有 `NeedBytes` 全程乘 1.6（`TempSpaceEstimate.cs:59`），而已经提交的 `MuxSegmentationTests.cs:28-30` 用的是"分段峰值 ≤ 0.65 × 余量"（不含 1.6）。两者同时套用等于把安全边际叠两次（§四 的 4K 例：不叠 1.6 = 112GB 能跑；叠了 = 179GB 仍被拒）。**这直接决定 4K 那个案例是"能跑"还是"继续拒绝"**，必须由人定口径（我倾向：分段项只用 0.65 额度，不再叠 1.6，并把上游在盘量如实计入总量）。
2. **上游在盘量是否计入守门？** 我按"计入"写（依据：`:503-508` 的低估事故）。若评审要求不计入，§四 的结论会整体变乐观，风险自负。
3. **Phase 2 是否本轮一起做？** 不做的话：4K 案例（新顺序）能跑但只留 19.9GB 余量、1080p 双开案例段被压到 1311 帧且余量为 0（§4.3）——即"1x/2x 配置下 Phase 1 基本不解决问题"。
4. **段下界 50 帧在流水线模式下是否要抬高？** 段越小，`每段一次编码器启动`（"秒级/次"，`MuxSegmentation.cs:20-21`）摊到每帧越贵：按 §4.3 的 28 段估，段启动开销可能到分钟级。要不要把流水线模式的段下界抬到（比如）300~500 帧，需要按"能接受的编码器启动次数"定。
5. **旧顺序（补帧在前）的上游单帧口径**：补帧输出的引擎直出 JPG 实测是 238KB → 737KB（3.1×，`TempSpaceEstimate.cs:6-7`），但在 `PeakFrameMegabytes(..., mult=1.0, frameInterp=true)` 里被 `max(S, …)` 的下限压平（`:40`）⇒ 用 `S` 计旧顺序的上游**可能偏低**。要不要给旧顺序上游单独一个口径（或实测标定一次），需要人定。
6. **段命令是否补 `-c:v mjpeg_cuvid`**（`:3786-3790` 单遍有、`:5232-5233` 段路径没有）：只影响解码速度，是否统一？
7. **段文件体积是否计入守门**：本文按"≈0.2GB/段、可忽略"处理（§4.1），要不要按码率显式入账？
8. **硬编失败重试**要不要下沉到"每段"（现在段失败 = 整任务失败，`:5236-5237`；单遍有 3 次重试，`:3918-3981`）？
9. **进度条方案三选一**（S7）：段编码期间不改进度条 / 独立 band / 只按台账推进 —— 需要产品口径决定。
