## 一、一句话口径

| 谁 | 干什么 |
| --- | --- |
| `AlhPro.Core.UpscaleRates`(内置表) | **他机(开发机)实测,只作资料与回归基线**;生产判定**不再取它的值**(只用于"选采样帧数"和单测对照) |
| `ImgUpscalerUI/UpscaleCalibrator` | 首次需要判定时,在**用户这台机器**上用真引擎**两点法**测一次超分单帧耗时(约 10~20 秒,一次性) |
| `ImgUpscalerUI/CalibMemory` | 把结果落盘到 `%LOCALAPPDATA%\ALHPro\settings\engine-prices.json`,按 **机器指纹** 归档,下次直接复用 |
| `AlhPro.Core.LocalPriceBook` | 纯逻辑:查找 / 1080p 折算 / 拒收条件 / JSON 编解码(有单测) |
| `AlhPro.Core.PipelineOrderPlan.Decide(..., localPrices, machineKey, backend)` | 生产判据:本机命中(**且后端一致**)⇒ 按本机单帧耗时判;**未标定 ⇒ 一律旧顺序(补帧→超分)** |

## 二、公式:两点法(为什么不是"总时长 ÷ 帧数")

引擎**每进程**有一次固定地板:启动 + 模型加载 + 首次着色器/管线创建。本仓库早已实测到这点
(`PipelineOrderPlan.cs` 类注释):**1 帧**目录 = 1.01~1.19 s/帧(其中地板 0.75~0.92 s),**40 帧**目录批跑只有
0.25~0.30 s/帧 ⇒ **地板约为单帧成本的 3 倍**。所以"跑一次取总时长÷帧数"测出来的是地板,不是单帧耗时。

标定跑**两次**(各自一次进程启动):

```
t1 = F + 1·p        ← 1 帧那次
tN = F + N·p        ← N 帧那次
⇒ p = (tN − t1) / (N − 1)      ← 秒/帧(采样分辨率下,已扣掉每进程地板)
⇒ F = t1 − p                   ← 每进程地板(只用于审计)
```

* `N` 的取法:`N = Clamp(floor(30 ÷ pEst), 4, 8)`,`pEst` = 内置表那一格按**源面积**折算(查不到用 1.0 s/帧,偏悲观)。
  便宜的模型多采几帧、贵的少采,**总等待被 30 秒量级框住**;`N < 4` 一律不可信(差值会被噪声吃掉)。
  代码:`AlhPro.Core.CalibrationSample.FramesFor` / `BudgetSeconds = 30` / `MinFrames = 4` / `MaxFrames = 8`。
* 【2026-09-27 提速】**贵档再封顶 4 帧**：每帧估值 ≥ `ExpensivePerFrame = 0.20 s` 时上限取 `MaxFramesExpensive = 4`（4 帧的差值 ≈ 3×每帧，远大于两次进程启动的地板抖动）；便宜档仍用满 8（降了差值过不了 `MinDeltaRatio` 噪声门槛）。作者机器实测 Real-CUGAN 2x：`1+8` 帧 **14.2 秒** → `1+4` 帧 **约 8 秒**。
* 采样帧来源:**复用已拆好的源帧** `framesIn` 里的 JPG(已含降噪/裁剪),从**中段等间隔**取 `N+1` 张
  (避开片头黑场/片尾定格);**不额外调 ffmpeg、不动用户的中间帧**。
  代码:`CalibrationSample.SampleIndices(frameCount, need)`。
* 判据统一用 **1080p 基准**的秒/帧:`p1080 = p × (2073600 ÷ 采样源面积)`(超分成本 ∝ 源面积;依据见
  契约 A2 与本仓库的面积线性验证:扣掉地板后 3.98 对面积比 4.00,偏差 −0.5%~−7%)。

## 三、判据与"采信"规则(不许拿别人的数字)

```
本机有这一格(模型键 × 引擎倍率 × 机器指纹一致)
    ⇒ u = 本机 p1080,Measured = true,理由里原样引用出处
      (本机实测 <UTC+8 时间> 两点法(1 帧 <t1>s + N 帧 <tN>s,源 W×H,后端 <后端标签>)→ p s/帧@采样分辨率,折算 1080p p1080 s/帧)
本机没有这一格
    ⇒ UpscaleFirst = false(旧顺序:补帧→超分),Measured = false
      理由含【本机未标定】+「内置表是他机实测,不作为本机判据,保守用旧顺序」
      并且**明说**日志里的 `u=0` 是"未采信任何单帧耗时",不是"免费"(2026-09-25 那次事故正是 u=0 被当成免费)
表里只有另一台机器的记录
    ⇒ 同上,并在理由里写明「另一台机器(<指纹摘要>)的标定,已忽略」(别人的记录留在文件里可审计,但不参与判定)
```

* **机器指纹** = GPU 名称 + 三个 ncnn 引擎可执行文件的标识(文件名 + 字节数 + 最后写入时间)。
  换显卡 / 换或重编引擎 ⇒ 指纹变 ⇒ 旧标定**自动失效并重标**。
* 顺序判据本身(`u` 与门槛 `k·(r_hi−r_lo)/(k−1)`、15% 安全边际、两侧总成本)**一字未改** ——
  改的只有"u 从哪来"。补帧锚点表仍是原口径(它与机器相关性低得多,且本轮 non-goal 明确不动)。
* 只有"**超分与补帧都要真跑**"时才标定(同一个守卫 `doUpscale && frameInterp && upscaleRuns` 的语义不变);
  不补帧 / 不超分时顺序无意义,标了也白花时间。

## 四、失败路径(全部"不中断任务")

| 情况 | 行为 |
| --- | --- |
| 本机没有标定 | **先标定再判定**(同一个任务内,判定点之前) |
| 标定成功 | `CalibMemory.Upsert` 落盘 + 本次直接用刚测出的数字判定(同一任务不标第二次) |
| 标定失败(引擎退出码非 0 / 崩溃 / OOM / 模型缺 / 文件被占) | **吞掉异常**、记日志 → 返回 null ⇒ 旧顺序 + 界面一句短话(不给静默) |
| 标定超时(> 180 秒,引擎卡住) | 放弃标定(只取消标定这次,不影响任务)⇒ 旧顺序 + 短话说明"超时" |
| 用户取消 | 立即返回 null;临时目录照样删干净 |
| 素材帧数不足(取不到 N+1 帧) | 跳过标定,如实报「素材帧数不足」⇒ 旧顺序 |
| 采样退化(`tN ≤ t1`,两帧差值被噪声/降频吃掉) | **拒收**(不许回退成 `总量÷帧数` —— 那正是把地板当单帧耗时的旧错)⇒ 旧顺序 |
| 算出单帧耗时 ≤ 0.0005 或 > 120 s/帧 | 拒收(明显异常)⇒ 旧顺序 |
| 标定文件缺失 / 截断 / 字段非法 / schema 不认识 | `All()` 返回**空表**,绝不抛;逐条校验,坏的只丢坏的那条 |
| 落盘失败(权限/磁盘) | 只记日志:本次仍按刚测出的数字判定,下次要重标 |

**临时目录**:`<workDir>\calib_in` / `<workDir>\calib_out`,在 `finally` 里删 —— 成功、异常、取消三条路都删。

**标定耗时与记账**:标定单独记成阶段 `阶段耗时(准备·超分单帧耗时标定): X 秒`,并写明"含两次引擎启动、
**不是每帧速率**";标定过程**不接**引擎的逐帧 progress(免得被当成任务的帧率喂进 ETA 记账)。
标定耗时由 `UpscaleCalibrator.LastTotalSeconds` 暴露,累计值由 **`ConsumeCalibratedSeconds()`(取一次就清零)**
消费。三个点的位置必须成对(2026-09-25 修订 · F2 + R1):

| 点 | 位置 | 频次 | 作用 |
| --- | --- | --- | --- |
| 归零 | `Views/VideoView.xaml.cs` **任务入口**(`var taskStart = …` 之后、逐 item 循环之前) | **每任务一次** | 丢弃"上一次任务在记账前就结束"留下的残留(否则会**扣到下一次头上** ⇒ 样本偏乐观) |
| 累计 | `UpscaleCalibrator`(标定结束时累加) | 每次标定 | 本任务内**所有视频**的标定之和(多视频也扣得住) |
| 扣减 | `Views/VideoView.xaml.cs` 记账行 `processSeconds = taskSpan − encSeconds − calibSeconds` | **每任务一次** | 真正把它从 `PerfMemory` 的每帧成本样本窗口里扣掉 |

【为什么归零点不能放在 `VideoService.ProcessVideoAsync` 入口(R1 的根因)】那个方法是**每个视频都跑一遍**的,
而扣减/记账是**全任务一次** ⇒ 两个视频的任务里:视频 1 现场标定累计 → **视频 2 的入口把值消费掉丢弃** →
记账时 `calibSeconds = 0`(标定墙钟照样进样本)。所以 `VideoService.cs` 里**不许再出现**
`ConsumeCalibratedSeconds()`,由 `LocalCalibrationWiringTests` 用源断言 + 三处相对顺序钉住
(清零 < 逐 item 循环 < 扣减 < 记账)—— **日志与账两半成对**。

**后端与样本的四条硬约束(2026-09-25 修订 · F1/F3)**:

* **I1** 落盘的单帧耗时,必须是在**该次运行真正用于超分的那条后端**上测出来的 —— 做法是把"探测 + 设备定稿"
  (`VideoService` 的 `if (upscaleRuns) { … }` 整段)提到标定与阶段顺序判定**之前**;
* **I2** 单帧耗时**按后端分格存与查**(`LocalPriceBook` 的 `Backend` 键):在 ncnn 上测的绝不用于 ONNX 运行
  (两层保证:判定喂进去的表已按后端筛过 + `Decide(..., backend:)` 把后端传进 Core,由 `Resolve` 机械过滤;
  显式传了**认不出**的后端名 ⇒ 一格都不命中,不当成"不过滤");
  【R2 · 2026-09-25】因为后端不匹配而弃用时,**理由里要像"另一台机器"那样明写出来**:
  「本机在**另一后端**(<X>)上测过这一格,与本次后端(<Y>)不一致 ⇒ 已忽略」,界面短话同样说
  「本机这一格是在另一后端 <X> 上标的,已忽略」—— 否则用户会以为"本机压根没标过",下次还在同一条路上白等。
  (两种不匹配同时存在时**机器指纹那条优先**;后端那条只在"同一台机器、只是后端不同"时出现。)
  判定结果**不变**(仍不采用、仍未标定 ⇒ 旧顺序);
* **I3** 样本输出为**黑帧 / 0 字节空帧 / 帧数对不上** ⇒ 拒收、不落盘(判黑**复用**批次循环那条
  `EngineService.IsBlackPng → FrameInspect.IsDefectiveFrame`,不新造第二套判据);
* **I4** 后端**未确认**(空串、空白、认不出的名字)⇒ `TryBuild` 拒收、`Resolve` 不命中、
  `CalibMemory` 读回时直接丢弃该条记录 ⇒ **既不会落盘,也绝不会被采用**;
* **F3** 另有**相对噪声门槛**:两点法差值必须 ≥ `CalibrationSample.MinDeltaRatio`(= 0.15)× 1 帧那次的
  耗时,否则视为与"两次进程启动的抖动"同量级而拒收(九条绝对阈值挡不住假精度)。

## 五、怎么看它生效了(用户视角)

一次"超分 + 补帧"的任务里,诊断日志(`%LOCALAPPDATA%\ALHPro\diagnostic.log`)会依次出现
(**下面尖括号 `<>` 里的都只是"当次的实际数值"的占位;字段名 / 标点 / 箭头与代码逐字一致**,2026-09-25 t30 按代码重新同步过一次):

* **判定前的第一行(这一行告诉你"这次要不要标定")**:
  `阶段顺序判据的准备:后端=ncnn-Vulkan(本机 GPU);本机这一格(模型 models-se:0 2x + 该后端)没有标定`
* **本机没标定过 ⇒ 同一个任务里现场标一次**(下面这几行是摘录,示例数值):
  `超分单帧耗时标定(准备阶段):引擎=realcugan 模型=models-se:0 倍率=2x、后端=ncnn-Vulkan(本机 GPU)、采样 9 帧(1920×1080 源)、机器指纹 <指纹摘要>;临时目录 <workDir>\calib_in / <workDir>\calib_out`
  → `超分单帧耗时标定:1 帧那次 2.55 s`
  → `超分单帧耗时标定:8 帧那次 14.1 s(平均 1.763 s/帧,含地板)`
  → `超分单帧耗时标定结束:耗时 17.3 秒(成功,结果已写入标定表) —— 这段时间单独记为「准备(超分单帧耗时标定)」,并由 VideoView 记账时从 PerfMemory 样本窗口扣除(见 docs《本机标定-超分单帧耗时》§六.5)`
  → `阶段耗时(准备·超分单帧耗时标定):17.3 秒(一次性;含两次引擎启动。该耗时会在本次任务结束时从 PerfMemory 的每帧成本样本窗口里扣除 —— 标定过程本身也不接逐帧进度)`
  → `顺序判定:<模型键> @ <倍率>x(本机实测出处:本机实测 <时间> 两点法(1 帧 <t1>s + <N> 帧 <tN>s,源 <W×H>,后端 <后端标签>)→ <p> s/帧@<W×H>,折算 1080p <p1080> s/帧) → u <u>s > 门槛 <门槛>s(超分很贵,先超分能少算补帧) → u=<u>s、r_lo=<r_lo>s、r_hi=<r_hi>s、门槛=<门槛>s、预估节省 <Δ>s(<pct>%) → 选择 新顺序(超分→补帧)`
* **已经是标定过的机器**:上面那段标定日志**不再出现**(第一行会写「…有标定」),判定直接引用 `engine-prices.json` 里的记录(仍需**机器指纹 + 后端**两重匹配)。
* **标定失败时**:文件里 `⚠ 超分单帧耗时标定未取得结果:<原因> —— 本次保守用旧顺序(补帧→超分),任务继续`;
  界面日志区同时一句短话 `本机超分单帧耗时没标定成功(<原因>)→ 本次保守按「补帧→超分」,不影响成片`。
* **因为"另一条后端"而弃用**时,界面短话会点名后端(免得你以为"本机压根没标过"):
  `顺序:补帧→超分(本机这一格是在另一后端 <后端标签> 上标的,已忽略;详情见诊断日志)`;
  同一台机器、确实没有这一格的标定时是:`顺序:补帧→超分(本机还没标定超分单帧耗时,保守不切换;详情见诊断日志)`。
* **口径出处(便于改代码时同步本文)**:`UpscaleCalibrator.cs:102 / :112 / :119 / :158`(`超分单帧耗时标定…` 那四行)、
  `VideoService.cs:2375`(`阶段顺序判据的准备…`)、`VideoService.cs:2423`(`阶段耗时(准备·超分单帧耗时标定)…`)、
  `PipelineOrderPlan.cs:218`(`顺序判定:…` = `Decision.LogLine`)、`VideoService.cs:2419 / :2464-2469`(界面短话)。
* **一处待修的小瑕疵(本轮只报告、不动代码)**:任务结算时还会再打一行,代码写的是 `$"· 顺序判定:{uOrderLog}"`,
  而 `uOrderLog = orderPlan.LogLine` 本身已带 `顺序判定:` 前缀 ⇒ 实际出现的是 **`· 顺序判定:顺序判定:…`**(前缀重复一次),
  行尾还有 `;【实际 vs 预估:未采集】…`。定位:`VideoService.cs:2447-2448` 与 `:4414`。

一眼确认"换机器会重标"的办法:把 `engine-prices.json` 里 `machineKey` 手改一个字 ——
下一次判定就会当成"另一台机器的标定,已忽略",并重新标一次(这个文件是给用户看的文本 JSON,不是二进制)。

**首次的代价(如实说明)**:第一次跑"超分 + 补帧"的任务(哪怕只是 3 秒预览)会**多花约 10~20 秒**做这次标定;
标定结果落盘后,同一台机器/同一引擎/同一模型倍率**再也不标第二次**(换素材、换分辨率、跑预览都是直接复用)。
界面在标定期间会显示一句短话「准备:正在按本机实测标定超分单帧耗时(<模型> <倍率>x,<N+1> 帧)…」,
标定成功后再补一句「已按本机实测标定:<模型> <倍率>x = <p> 秒/帧(已扣引擎地板)」,
所以它看起来是"在准备",不是卡死。

## 六、已知限制(逐条照 §5 写清,不许含糊)

1. **标定测的是"第 1 批"那条后端;中途换后端会有偏差**。批次循环每一批都会重新判 ncnn / ONNX,而且
   `ncnnUnreliable` 可能在黑帧防御里**中途翻真**(之后各批改走 ONNX)⇒ 那时实际耗时与标定值会有偏差
   (契约 §5.1)。【2026-09-25 修订 · F1】"探测 + 设备定稿"**已上移到标定与判定之前**
   (`VideoService` 的 `if (upscaleRuns) { … }` 整段),所以标定测到的后端**按构造就是第 1 批真跑的那一个**
   (同一个纯函数 `AlhPro.Core.UpscaleBackendPlan.UseOnnx` + 同一套参数,不再是"开跑前另算一次取值");
   而且单帧耗时**按后端分格存**(I2)⇒ 中途翻成 ONNX 之后也不会去借用 ncnn 那一格。偏差因此被限制在
   "第 1 批之后那几批的实际耗时"上,**不会污染判定与落盘**。
2. **`VideoPipeline.cs` 的 ETA 每帧常数仍是开发机数字**(只影响"预计剩余时间",**不影响阶段顺序**)。
   本机 `PerfMemory` 会在跑过一遍后用实测修正 —— 属另一条线,本轮不改(契约 §5.2)。
3. **采样帧来自本次素材**;换素材(分辨率/内容差异大)且面积折算不成立时会有误差。面积线性有本仓库实测支持
   (扣掉地板后比值 3.98 对 4.00,偏差 −0.5%~−7%),但**仍不是严格线性**(契约 §5.3)。
4. **两点法用两次进程启动,GPU 热降频会让两次的"地板"不同**(实测同机样本离散可达 1.9×)⇒ 标定结果按
   "一次快照"对待,**不**声称是永远准确的真理(契约 §5.4)。单帧耗时被拒收的边界(≤0.0005 / >120 s/帧)就是
   为这种脏样本设的兜底。
5. **【2026-09-25 已修 · F2 + R1】`PerfMemory` 的样本窗口不再含标定墙钟 —— 这条声明现在是普遍成立的

## 七、数字口径(防止"同一个数字两种说法")

**凡是引用构建/测试数字,必须连命令与模式一起写** —— 同一棵树在不同模式下结果不同(2026-09-25 修订 · R3):

| 数字 | 命令 | 模式 | 实测 |
| --- | --- | --- | --- |
| UI 工程警告/错误 | `dotnet build alh-pro\ImgUpscalerUI\ImgUpscalerUI.csproj -c Debug -p:Platform=x64 -v m` | **全量重建**(命令末尾加 `/t:Rebuild`) | **71 警告 / 0 错误**(稳定、可复现)。范围说准(**2026-09-25 t30 修订 · t42 的 low**):**本机标定新增的 5 个文件**(`UpscaleCalibrator.cs` / `CalibMemory.cs` / `LocalPriceBook.cs` / `CalibrationSample.cs` / `UpscaleBackendPlan.cs`)**0 条警告**;但**标定接线所在的 `VideoService.cs` 有 4 条旧有警告**(`:5576 CS8602`、`:7540 CS0219 ×2`(histDelCnt / groupMarksCnt)、`:7740 CS0219` slotDone) —— 这 4 条都在**本轮未改动区**、不是标定引入的。原话「其中没有一条来自本机标定相关文件」范围过宽,已改成本口径(repo 里 warning 最多的仍是 `VideoView.xaml.cs` 25 条) |
| UI 工程警告/错误 | 同上 **但不加** `/t:Rebuild` | **增量**:只报"这一次真正重编译的那部分文件"的警告 | 实测出现过 **0 / 35 / 70** 三种(取决于改了几个文件、MSBuild 重编了多少)⇒ **这个数字本身没有可比性** |
| 测试 | `dotnet test alh-pro\AlhPro.Tests\AlhPro.Tests.csproj -c Debug /t:Rebuild --nologo` | 全量重建 | **失败 0 / 通过 1420 / 总计 1420** |

【规矩】引用警告数时**一律引用全量重建那一次的 71**(并写出 `/t:Rebuild`);若引用增量数字,
必须同时写清"增量、本次重编译了哪些文件",否则就是无口径的数字(t37 交付说明里那句"70 警告"
正是被独立复核点名的例子 —— 同一个工作区,增量 70、全量重建 71,两个数都对但口径不同)。
测试条数同理:必须是"`/t:Rebuild` 全量"这一次的数字,不拿历史某次的数字充当现状。
