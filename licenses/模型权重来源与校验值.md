## A. Real-CUGAN（2026-09-24 重新随包）

### A1. 引擎（本仓库用 2025/2026 版 ncnn 重编）

| 文件 | 体积 | SHA256 |
|---|---|---|
| `发布版\engines\realcugan\realcugan-ncnn-vulkan-2026.exe` | 36,407,012 B | `E141604F16AFFB9A4631955B320511F1642780068452754D9FA5D730F545D729` |

* **前端源码**：`https://github.com/nihui/realcugan-ncnn-vulkan`（MIT © 2019 nihui）。
  实测 `master` 与 release tag `20220728` 的 `src/{main.cpp,realcugan.cpp,realcugan.h}` **逐字节同长同内容**，
  所以取件用 `master` 与用发布版本的源码是一回事。
* **唯一改动**：MinGW 宽字符 printf 兼容补丁 —— `swprintf(..., L"%s/up%dx-...", model.c_str(), scale)`
  → `L"%ls/up%dx-..."`（6 处）。MinGW 按 C99 把宽格式串里的 `%s` 当**窄**串，
  不改会把权重目录名截成首字节（`models-se` → `m`）⇒ 引擎找不到权重、**只画一张坏帧、exit=0**。
  与 Real-ESRGAN 重编时踩的是同一个坑（`ENGINE_REALESRGAN_REBUILD.md`）。
* **推理库**：ncnn master 源码（BSD-3 © Tencent），`NCNN_VULKAN=ON`、
  `NCNN_VULKAN_ONLINE_SPIRV=ON`（本前端内嵌 GLSL、运行时编译 SPIR-V）、`NCNN_SYSTEM_GLSLANG=ON`、
  静态链接 glslang/SPIRV/webp/gomp（**不需要随包任何第三方 DLL**）。
* **构建要点（下一步会踩的坑，已实测）**：ncnn 的 `InnerProduct_vulkan::create_pipeline`
  内部会 `create_layer_vulkan(LayerType::Flatten)`，`Convolution_vulkan` 内部会建 `Reshape`/`Padding`。
  若按 Real-ESRGAN 那份 `WITH_LAYER_*` 清单裁层（它把 `flatten`/`reshape` 关掉了），
  这两个内部子层会返回 **NULL 并被直接解引用 ⇒ 启动即访问违例（0xC0000005，0 帧产出）**。
  本引擎的做法：**不裁层**（全部 `WITH_LAYER_*` 保持 ON）。
* **为什么要重编**：官方 `20220728` 那份 exe 实测 `VK_EXT_robustness2` 出现 **0 次**
  （与 Real-ESRGAN 官方 2022 版逐项同类）⇒ 在 NVIDIA 50 系（Blackwell）上属「退出码 0、却输出坏帧」那一类。
  重编后指纹与 `realesrgan-ncnn-vulkan-2026.exe` **逐项一致**（`robustness2`=2、`VK_KHR_cooperative_matrix`=364 …）。

## C. 本机实测（RTX 4060 Laptop 8GB / 驱动 572.83；素材：1080p 40 帧 PNG，与超分/补帧同一批）

> 口径统一：**串行跑、机器空闲**、各两次冷跑、进程级计时。
> （注：t2 文档里 617~628 ms/帧 那组数字量自**官方 20220728 引擎**；本表同时给出官方与重编版，用来暴露差异。）

### C1. 超分（1080p → 3840×2160，`-s 2 -t 0 -g 0 -f jpg -j 1:1:1`）

| 引擎 / 模型 | 命令 | ms/帧 | 结论 |
|---|---|---|---|
| Real-CUGAN **重编版**（随包），`-n -1` | `realcugan-ncnn-vulkan-2026.exe -i in40 -o out -s 2 -n -1 -m models-se -t 0 -g 0 -f jpg -j 1:1:1` | **1565.9 / 1594.9** | 能跑、3840×2160、画面正常（sample mean 193.06），**但慢** |
| Real-CUGAN **重编版**，`-n 0` | 同上换 `-n 0` | 1742.8 / 1628.1 | 与保守档同档 |
| Real-CUGAN **重编版**，`-n 3` | 同上换 `-n 3` | 1652.7 / 1607.4 | 与保守档同档 |
| Real-CUGAN **官方 20220728**（不随包） | 同名参数 | **603.9 / 592.5** | 快 2.7×，但 **50 系会出坏帧**（`robustness2`=0）⇒ 不能发 |
| Real-ESRGAN animevideov3 x2（随包，2026 重编） | `realesrgan-ncnn-vulkan-2026.exe … -n realesr-animevideov3` | 255.8 / 255.9（t2 §1.1） | 同样素材的参照 |

**"好不好用"结论（Real-CUGAN）**：画质上它是动漫线条最干净的一档（与 animevideov3 的逐图 PSNR = 32.6 dB，
说明两者确实是不同算法）；**但速度是 6 倍代价**（1.57 s/帧 vs 0.26 s/帧）。
⇒ 实话说：**它适合"少量精品镜头把线条做干净"，不适合整片批量**；下拉提示里已如实写实测秒数，不写"更快"。
另：**必须 GPU** —— 它只有 ncnn-Vulkan 权重，CPU 档（`-g -1`）在重编版上实测访问违例退出（0 帧产出），
没有可用显卡时软件会**明确拒绝**并提示改选 Real-ESRGAN（不静默换模型）。

据此说"v4.26 更快"。本次在**空闲机器**上复测，三支都是 80~84 ms/输出帧 —— **"v4.26 更快"不成立**，
它是"同速、更晚一版"。上架理由改为"用户确认上架 + 同速同功能"，不再宣称更快。

### C3. IFRNet 为什么**没接**（如实回报，不是漏做）

1. **50 系必须先重编**：官方 `20220720` 那份 exe 实测 `VK_EXT_robustness2` = **0 处**
   ⇒ 与 Real-CUGAN 官方包同代、同属"Blackwell 上退出码 0 + 坏帧"那一类（要么重编、要么走 ONNX，
   而它也没有 ONNX 权重）。
2. **实测更慢**：最快的一支（S_GoPro）180.8 ms/输出帧，是我们现有 RIFE 三支（约 81 ms）的 **2.2 倍**。
3. **只有 GoPro 系支持任意帧数/时间步**：另外三支（Vimeo90K 系）在 `-n` 下直接拒绝
   （逐字 `only GoPro model support custom numframe and timestep`）⇒ 接进来还得为"哪几支不能用任意帧数"
   再开一条语义分支，而 `VideoService.IsV4Model` 现在把非 v4 一律按 2x 级联处理。
4. 定位上它是 CVPR 2022 的 **"Efficient"** Frame Interpolation（主打轻量），
   在动漫素材上并不比 RIFE 族更强，而我们的 RIFE 族已经在包里。
   ⇒ **既不更快也不更好看，不接**（按用户"只要好用就行、不许凑数"的口径）。

### C4. GMFSS 为什么**先放一放**（队长 2026-09-24 裁定）

1. 现成构件只有 `Justin62628/gmfss-ncnn-vulkan` 的 release `v0.0.0`
   （90,139,233 B，标题逐字 **"For CPU 576p inference only"**）⇒ 要 GPU / 1080p 得自己转换、可能还要重编；
2. 队长实测经 `gh-proxy.com` 镜像下载 **30 分钟只到 11.6 MB / 86 MB**（截断、不可解压）——取证成本高；
3. 转换器 `Justin62628/gmfss-to-ncnn` 是 **GPL-3.0**：只能本机用它转模型，**绝不进包、不链接进产品**。
   ⇒ 本轮**不随包 GMFSS 权重、不接 GMFSS 引擎**。将来若要做，前置条件是：以 ALH Pro 名义拿到作者本人
   （`98mxr`）的书面许可 + 解决 GPU/1080p 的模型转换。
